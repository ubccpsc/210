# Why CPSC 210 exists

Software construction looks different now than it did before LLMs became competent at generating code that often actually works. As we start this course, you are setting out to learn how to construct software at the moment LLMs have learned to write code based on a natural language prompt. This reading makes a case for why software construction is a skill with a future, rather than being one that has been relegated to history.

## Programming was never the important part of software engineering

We start with an admission: Programming, the act of converting a clear description of a problem into working syntax, is being increasingly automated. And if that were all software engineering was, the job might be superseded by technology. But typing syntax was never what software engineering was about. It was the part of the job that looked like the job, but it wasn't the _important_ part of the job.

Programming is the act of producing a working program. Software engineering is the discipline of building and evolving systems that stay valuable over a long life: one that teams of people can work on, that is dependable, and that can evolve to meet needs no one has thought of yet. Software engineering has been referred to as _"programming integrated over time"_. That is, programming deals with a single instant, whereas software engineering concerns the whole lifetime of a system, at scale, deployed in the world. Programming is a part of software engineering, but it is only a small part. The activity being automated by LLMs is programming. The discipline this course is about is software construction, and most of it lies exactly where the automation does not reach: deciding what to build, keeping a growing system understandable, and making sure it can still be changed safely in the future.

## LLMs: the third phase of software disruption

This is not the first time what programming looks like has significantly changed. Decades ago Fred Brooks divided the difficulty of building software into two kinds. Incidental complexity is the difficulty we manufacture for ourselves: fighting language syntax, boilerplate code, and all of the lines of setup and test code that stand in front of the one line change we want to make to a program. Essential complexity is the difficulty inherent in the problem: deciding what the system must do, how to design it so the parts fit together, so that changing one does not quietly break the rest, and understanding what it even means to be correct. Brooks argued that no single tool would ever yield an order-of-magnitude gain, because tools only ever reduce incidental complexity, and the essential complexity is what is really hard about software engineering.

The history of the field is largely the history of reducing incidental complexity, and the profession has survived, and thrived, through at least three major phases of change. The first was the move from assembly language to high-level languages, when compilers took over turning human-readable high-level language source code into machine instructions, which freed engineers to focus much more directly on what they actually wanted their programs to do, not how they did it. The second was reuse: shared libraries, frameworks, and REST-based services served over the network, which meant that systems could be composed from rich building blocks instead of always being built from scratch. Both of these changes induced the same worry: that building software would now need fewer people, or less skill. Each instead just increased the complexity of the problems we were able to solve, and each new generation of program is more complex and featureful than the last. Large language models are the latest phase of change, and the broadest of the three. They reduce incidental complexity not one layer at a time but across the breadth of tasks software engineers perform. As with past waves though, this reduction in incidental complexity is only going to increase the complexity and scope of the problems software engineers will be able to tackle now that the incidental complexity they have been fighting for decades has been reduced.

## What software engineering becomes

When code was expensive to produce, the scarce resource was people who could produce it. Now that code is close to free, the scarce resource is something else. Anyone can generate ten thousand lines in an afternoon. The systems that endure are not the ones with the most code, but the ones a human can still understand a year later, and still effectively evolve when a new feature is needed or it fails in the middle of the night. An LLM will produce a lot of plausible, locally sensible code far faster than any person, but under scrutiny this code is often globally incoherent, poorly decomposed, and weakly validated.

A shrinking share of what software engineering is about is writing code. A growing share is judging whether code is correct and whether it can be evolved, and this is the harder of the two. It is easy to believe you understand code you wrote yourself because you put sustained effort into designing and writing it yourself. It is much harder to understand code you are only reading, whether it came from another engineer or an LLM. The shift from author to editor does not lower the demand for construction knowledge: it raises it as the volume of change and complexity of systems grows every single day.

## Why we still teach you to write code

We aren't teaching you to write code by hand because we expect this to be a dominant part of your career.
We are teaching you to write code because the understanding needed to direct and correct a machine cannot be acquired by watching one work. It is taught by doing the thing yourself: by writing the code, experiencing an unexpected fault, and learning how to resolve it. Reading code teaches you a little. Writing it, and constantly evaluating the strengths and weaknesses of different alternatives, provides the real lessons. Without these, you are not positioned to evaluate what an LLM produces. You can only take it or leave it on faith, which is neither judgement nor agency.

We build software to make a computer do useful work for us, and the only way to tell a computer precisely what work to do is by expressing our intent in source code. A prompt written in plain language is a request, but different LLMs will generate different programs, each of which may behave in subtly different ways. Source code is not a request. It is the exact instruction the machine carries out, expressing what is to be done without ambiguity. This is why we do not program in English: not because the tools are not yet good enough (as LLMs are starting to become), but because English is ambiguous in a way a computer cannot deterministically overcome.

## A systematic process

Engineering large-scale real-world software systems is not improvised. It is a systematic process, regardless of who or what writes the source code. The process begins by determining precisely what the system is actually meant to do, and stating those requirements clearly enough that they can be implemented. Once implemented, we also need to know precisely what behaviours are valid and invalid. We also need to ensure the implementation itself is in a form that does not close the door to future evolution to new and unexpected features. LLMs are adept at the middle implementation piece. They do not do the systematic thinking on either side of it. We spend much of our time in this course thinking carefully about these three aspects: what is being built, whether it is designed to afford change, and whether it is correct. But without knowing how to write code, these tasks cannot be completely and effectively performed.

Ultimately, software is built to perform useful work for humans. Software engineers will continue to play a crucial role in ensuring the software that is built meets real needs, and provides lasting and durable value in the future. Regardless of how effective LLMs become at automating the incidental parts of the profession, these essential tasks will remain.
