# Why CPSC 210 Exists

Software construction looks different now than it did before LLMs became competent at generating code that often actually works. As we start this course, you are setting out to learn how to construct software at the moment LLMs have learned to write code based on a natural language prompt. This chapter makes the case for why software construction is a skill with a future, rather than one that has been relegated to history.

## Programming Was Never the Important Part of Software Construction

We start with an admission: programming, the act of converting a clear description of a problem into working syntax, is being increasingly automated. And if that were all software construction was, the skill might be superseded by technology. But typing syntax was never what software construction was about. It was the part of the job that looked like the job, but it wasn't the _important_ part of the job.

Programming is the act of producing a working program. Software construction is the discipline of building and evolving systems that stay valuable over a long life: systems that teams of people can work on, that are dependable, and that can evolve to meet needs no one has thought of yet. This discipline has been described as _"programming integrated over time"_ (a phrase from the book _Software Engineering at Google_). That is, programming deals with a single instant, whereas construction concerns the whole lifetime of a system, at scale, deployed in the world. Programming is a part of software construction, but it is only a small part. The activity being automated by LLMs is programming. Most of software construction lies exactly where the automation does not reach: deciding what to build, keeping a growing system understandable, and making sure it can still be changed safely in the future.

## LLMs: The Third Phase of Software Disruption

This is not the first time what programming looks like has significantly changed. Decades ago Fred Brooks divided the difficulty of building software into two kinds. Incidental complexity is the difficulty we manufacture for ourselves: fighting language syntax, boilerplate code, and all of the lines of setup and test code that stand in front of the one line change we want to make to a program. Essential complexity is the difficulty inherent in the problem: deciding what the system must do, how to design it so the parts fit together and changing one does not quietly break the rest, and understanding what it even means to be correct. Brooks argued that no single tool would ever yield an order-of-magnitude gain, because tools only ever reduce incidental complexity, and the essential complexity is what is really hard about building software.

The history of the field is largely the history of reducing incidental complexity, and the profession has survived, and thrived, through two earlier phases of change. The first was the move from assembly language to high-level languages: compilers took over turning human-readable source code into machine instructions, which freed engineers to focus on what they wanted their programs to do, not how they did it. The second was reuse: shared libraries, frameworks, and services offered over the network, which meant that systems could be composed from rich building blocks instead of always being built from scratch. Both of these changes induced the same worry: that building software would now need fewer people, or less skill. Each instead increased the complexity of the problems we were able to solve. Large language models are the third phase of change, and the broadest of the three. They reduce incidental complexity not one layer at a time but across the breadth of tasks software engineers perform. As with the past waves, the scope and ambition of the systems we attempt will grow with them.

## What Software Construction Becomes

When code was expensive to produce, the scarce resource was people who could produce it. Now that code is close to free, the scarce resource is something else. Anyone can generate ten thousand lines in an afternoon. The systems that endure are not the ones with the most code, but the ones a human can still understand a year later, and still effectively evolve when a new feature is needed or it fails in the middle of the night.

A shrinking share of what software construction is about is writing code. A growing share is judging whether code is correct and whether it can be evolved, and this is the harder of the two. It is easy to believe you understand code you wrote yourself because you put sustained effort into designing and writing it yourself. It is much harder to understand code you are only reading, whether it came from another engineer or an LLM. The shift from author to editor does not lower the demand for construction knowledge: it raises it as the volume of change and complexity of systems grows every single day.

## Why We Still Teach You to Write Code

We aren't teaching you to write code by hand because we expect this to be a dominant part of your career. We are teaching you to write code because the understanding needed to direct and correct a machine cannot be acquired by watching one work. It is taught by doing the thing yourself: by writing the code, experiencing an unexpected fault, and learning how to resolve it. Reading code teaches you a little. Writing it, and systematically evaluating the strengths and weaknesses of different alternatives, provides the real lessons. Without these, you are not positioned to evaluate what an LLM produces. You can only take it or leave it on faith, which is neither judgement nor agency.

We build software to make a computer do useful work for us, and the only way to tell a computer precisely what work to do is by expressing our intent in source code. A prompt written in plain language is a request: different LLMs will generate different programs from the same prompt, and each may behave in subtly different ways. Source code is not a request. It is the exact instruction the machine carries out, and it declares, without ambiguity, how the program will behave every time it runs. Whatever tool produces it, the behaviour of a software system is ultimately stated in its code. Source code will therefore remain the lingua franca of software systems, and practitioners must be adept at understanding, judging, evolving, and creating it.

## What This Course Teaches

Constructing real-world software systems is not improvised. It is a systematic process, regardless of who or what writes the source code. That process begins before any code is written, in deciding precisely what the system must do, and continues after, in verifying that the behaviour is correct and designing the implementation so that future change stays possible. LLMs are adept at the implementation in the middle; they do not do the systematic thinking on either side of it. That thinking is what this course spends its time on: stating what is being built, judging whether it is correct, and designing it to afford change, together with the construction skill that makes those judgements possible.
